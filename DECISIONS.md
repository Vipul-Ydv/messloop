# Decisions

One line each, as the brief asks (§0.1.5).

- **AI provider:** our own model — Qwen3-4B (Apache-2.0, Q4_K_M) served by llama.cpp on an Amazon EC2 c7i.2xlarge, called through its OpenAI-compatible API with a JSON-schema grammar. Bedrock is `NOT_AUTHORIZED` on our account, so per R13 it is not claimed anywhere.
- **Model size:** Qwen2.5-1.5B was tried first; it was fast enough but attributed vote shares to the wrong dish. Qwen3-4B gets the facts right at ~9 tokens/s on CPU.
- **Thinking off:** Qwen3's reasoning mode is disabled per request (`enable_thinking: false`); the evidence is already computed, so it only adds latency.
- **AI runs in the background:** a model answer takes ~25 s, close to API Gateway's 30 s cap. `generate` stores the recommendation at once with the deterministic template (`aiStatus: "running"`), then the Lambda invokes itself asynchronously to ask the model and swap in the validated text. Decisions are refused while it runs; after 2 minutes a run is treated as finished so it can never block the manager.
- **Extra validator checks:** a replace action must name a replacement (and only a replace may); a replacement needs at least 3 occurrences; a vote share must belong to the dish it is written next to; comparisons between candidates ("lower waste than", "most votes") must match their numbers, attributed to the dish named just before the claim.
- **Prompt shape guide:** the spec's system prompt stays verbatim; a placeholder template in the user message asks for each alternative's own numbers rather than comparisons, which a small model gets wrong.
- **Tests:** Node's built-in runner with `--experimental-strip-types` — no test dependencies.
- **Validator constants:** the numbers 100 ("per 100 servings"), 5 ("out of 5") and 3 (the rules' minimum) may appear in model text without being in the evidence.
- **Validator tolerance:** a model number matches an evidence number if it is within 0.05, i.e. rounded to one decimal.
- **Model JSON:** if the reply wraps JSON in prose or code fences, the outermost `{...}` is parsed — then every check still applies.
- **Evidence package:** history is oldest-first; derived values are rounded to 2 decimals so the model restates readable numbers.
- **Seed:** `includeLatest=false` leaves out the 8 Oct Aloo Gobi record so the demo can log it live; the baseline still lands on 18.23 once it is in.
- **Seed data lives in `packages/core/seed-data.ts`**, shared by the tests and the backend seed, so the demo and the golden tests cannot drift.
- **Fallback template:** average rating shown to one decimal.
- **Frontend hosting:** S3 static website, served over HTTPS from the bucket's S3 endpoint (`infra/frontend-hosting.yaml`). Amplify Hosting is at our account's one-app quota (used by another project) and CloudFront needs account verification, so neither is claimed (R13).
- **Routing:** hash routes (`#/dashboard`), so the static site needs no server rewrites.
- **Live preview uses `packages/core`:** the entry form imports `wastePct`/`wastePer100` directly, so the preview and the stored value come from the same code.
- **Student view:** students can read trials and their impact (`GET /interventions`, `/impact`); everything else stays manager-only.
- **CORS preflight:** the catch-all route also receives `OPTIONS`; the Lambda answers 204 and API Gateway adds the CORS headers.
- **The waste agent (after DTU judges asked for agentic AI and more AWS):** logging a meal starts it through DynamoDB Streams (filtered to new, non-seeded waste records). An AWS Step Functions state machine (`messloop-agent`) runs Investigate → WaitForManager → done, or MeasureImpact for meals logged under a trial.
- **Agent tools:** our model picks which evidence to look at (`get_waste_history`, `get_student_feedback`, `get_replacement_options`); each tool returns a slice of the evidence package code already computed. The validator only accepts numbers from the slices the agent actually looked at.
- **Human in the loop is a real pause:** WaitForManager uses a Step Functions task token. Only the manager's decision resumes the run; recordDecision is still the only code that changes status (R1).
- **Separate agent Lambda (`messloop-agent`, 300 s):** the HTTP API never calls the model, so it stays well inside API Gateway's 30 s.
- **Field-level writes:** the pause token and the decision are written with DynamoDB update expressions (decision-side conditional on `pending`), so the two can't overwrite each other.
- **Outcome report:** after a trial meal the agent writes one sentence about what changed (numbers checked, must say "per 100 plates"); code always appends the observed-change caveat, so the model can't drop it.
- **Demo mode:** one-click demo logins (`POST /auth/demo`, `DemoMode` parameter, on by default) because a judge without a role code got stuck at DTU. Safe only because all demo data is simulated and a manager can reset it; turn it off for real data.
- **Voice call instead of a phone call:** mess staff answer five spoken Hindi questions in the app (Amazon Polly, voice Kajal). It runs like a call: question, beep, listen, and it moves on by itself after a 1.5 s pause (the room's noise level sets the threshold). A real phone line (Amazon Connect) is the next step: new-account limits and Indian number paperwork made it too risky for the deadline.
- **Streaming, one answer at a time:** each answer is sent as 16 kHz PCM the moment it ends, while the next question plays, and transcribed with Amazon Transcribe streaming (hi-IN) in about the time it took to say. Batch jobs took 10-15 s each and only started after the call; the wait after hanging up went from about 25 s to about 2 s.
- **Rules before the model:** Transcribe usually writes numbers as digits, so `packages/core/voice-parse.ts` reads them (and dish names, in Hindi or English) with tested rules. Our model is asked only about an answer the rules couldn't read, such as numbers spoken as words.
- **Voice never saves on its own:** the values fill the form with "Heard: …" under each field, and the worker presses Save. In testing, Transcribe heard "तेईस" (23) as "30", which is exactly why.
- **No recordings are stored:** audio goes straight to Transcribe and is discarded; only the text is kept, and only once the worker saves.
- **Staff reason and entry method** are stored on the waste record (`staffReason`, `entryMethod: voice|form`); they are not yet part of the evidence the model sees.
- **The agent sends alerts by itself:** "suggestion ready" after it investigates, "trial result" after it measures, and a 3 pm daily reminder (EventBridge Scheduler, Asia/Kolkata) when no meal was logged that day. Each is stored for the dashboard and published to an SNS topic; email goes out only when the `AlertEmail` parameter is set (AWS sends a confirmation link first), and the app only says "emailed" in that case. SMS was skipped: Indian SMS needs DLT sender registration.
- **Student feedback:** an anonymous rating (1-5) plus up to three reasons, added to the dish's rating counts the agent already reads, so students' reasons reach its next suggestion. Seeded aggregates are kept and marked with how many real votes were added (`realVotes`); a phone remembers it voted today, nothing more.
- **Students say what should be made instead:** a one-tap vote for another dish the mess cooks goes into that dish's replacement poll, the same evidence the agent reads (a new poll lists every other dish, so one vote never narrows the agent's options). Ideas typed in their own words go to the manager only: a dish with no waste history can't be compared, so the agent never sees them.
- **Impact in plates and CO2e:** food saved ÷ what each student actually ate per plate after the change, and food saved × 2.54 kg CO2e/kg (FAO 2013 global average, 3.3 Gt CO2e / 1.3 Gt). Both are labelled Estimated, shown only when food was saved, and the CO2e is described as the food's footprint, not methane from this mess.
- **Scope cut for time:** no Analytics page and no P1 features; Dashboard carries the core charts.
